# 주간 메일 · 판정 변화 알림 · 효과 결과 알림 — 설계안

2026-11-22 작성 · 상태: **설계안 (구현 전)** · 관련: 기획서 로드맵 「보드 저장 · 주간 메일」(나중)

> 이 문서는 "다시 올 이유"를 만드는 알림 3종의 설계다. 코드는 아직 없다.
> 정할 것(§8)이 정해지면 구현 순서(§9)대로 진행한다.

---

## 1. 왜

- 지금 SiteKPI는 사용자가 **직접 찾아와야만** 가치가 생긴다. 대상 고객(초보 운영자, 보고가 필요한 담당자)은 GA4 화면 자체를 잘 열지 않는 사람들이다.
- 보드에는 이미 "보내기 좋은 글"이 있다: 総評 한 문장, まとめ 4줄(いまの状態 · いちばんの課題 · まずやること · 次に確かめること), 「報告用にコピー」.
- 재방문 지표(기획서 #analytics 「재방문」: 첫 `login` 후 7일·28일 안의 `board_view`)를 움직이는 가장 직접적인 수단이다.

## 2. 알림 3종

| 종류 | 언제 | 내용 | 기본값 |
|---|---|---|---|
| **A. 주간 메일** | 매주 월요일 08:00 (사용자 시간대, 기본 Asia/Tokyo) | 総評 한 문장 + まとめ 4줄 + 숫자 3개(주전환 건수 · 주전환율 · 一番の課題) + 「ボードを開く」 | 구독한 사람만 |
| **B. 판정 변화 알림** | 매일 확인, **바뀌었을 때만** | "「カート→購入率」が 目安内 → 要注意 になりました" + 전주 대비 + 「今見るべきこと」 링크 | A를 구독하면 함께 켜짐(끌 수 있음) |
| **C. 효과 결과 알림** | 대책 공개일 + 15일째 아침 (보드의 「やった日を記録」) | "「送料を先に表示」の前後 14 日: カート→購入 14.6% → 18.2%" + 6 効いた？ 링크 | 공개일을 기록한 사람만 |

원칙
- **소음보다 침묵.** B는 判定(良好 · 目安内 · 要注意)이 바뀐 지표만, 하루 최대 1통, 같은 지표는 7일에 한 번.
- **보드와 같은 글.** 메일 문장은 `views/story.py` · `story_l10n.py`가 만든 문장을 그대로 쓴다(새 문구 체계를 만들지 않는다). 언어 = 구독 시 언어(ja/en/ko).
- **메일 안에 GA4 원자료를 늘어놓지 않는다.** 숫자는 보드 상단과 같은 3개까지. 자세한 건 보드에서.
- 30명 미만 등 「少ないため参考」 상태면 B·C는 보내지 않는다.

## 3. 사용자 흐름

1. 보드 まとめ 카드 아래 「毎週メールで受け取る」 → 작은 팝업: 메일 주소 · 요일/시간 · 언어 · (B 함께 받기 ☑).
2. 확인 메일(더블 옵트인) → 링크를 누르면 구독 시작. 누르지 않으면 7일 뒤 삭제.
3. 모든 메일 하단: 「配信停止」(원클릭, 로그인 불필요, `List-Unsubscribe` + `List-Unsubscribe-Post` 헤더) · 「設定を変える」.
4. 설정 화면(/settings)에 「メール」 카드: 받는 알림, 요일/시간, 정지.

## 4. 가장 큰 기술 과제: 사용자가 없을 때 GA4 읽기

지금 구조로는 **보낼 수 없다.**

- GA4 토큰은 **세션**(Fernet 암호화, 14일 TTL)에만 있다. 사용자가 14일 오지 않으면 사라지고, 세션 밖(스케줄러)에서 읽을 방법이 없다.
- OAuth는 이미 `access_type=offline` + `prompt=consent`라 **refresh token은 받고 있다.** 따로 오래 보관하지 않을 뿐이다.
- 메일 주소도 없다. 권한이 `analytics.readonly` 하나라 Google 계정 메일을 모른다(`ga4_email`은 데모에서만 채워짐).

해결안

| 항목 | 안 |
|---|---|
| 토큰 보관 | 구독할 때만, 그 속성 하나의 refresh token을 별도 저장소 `subscriptions`(Firestore `sitekpi/subscriptions/rows/{id}`)에 **암호화해서** 저장. 키는 세션과 분리(`SUBSCRIPTION_ENCRYPTION_KEY`, Secret Manager). 구독 해지 · 연결 해제 · `invalid_grant` 시 즉시 삭제 |
| 메일 주소 | 사용자가 직접 입력(더블 옵트인으로 확인). Google `email` scope를 추가하는 안도 있지만 동의 화면 문구가 바뀌고 심사 설명이 늘어나서 **입력 방식을 권장** |
| 실행 | Cloud Scheduler(매시 정각) → Cloud Run의 `POST /cron/notify` (OIDC 토큰 검증, 외부 호출 차단). 그 시각에 보낼 구독만 처리 |
| 계산 | 기존 함수 재사용: `fetch_pack_overlay` · `fetch_flow` · `fetch_story_x` → `build_story`. 사용자 세션 대신 구독 행으로 만든 세션 모양 dict(`portfolio._sub_session`과 같은 방식) |
| 판정 기억(B) | 구독 행에 지난 判定 스냅숏 `{bench_key: "up"|"mid"|"down"}` + 마지막 알림 시각 |
| 효과(C) | 지금 대책 공개일은 세션(`story_releases`)에 있다 → 구독자는 구독 행에도 복사. 비구독자는 기존대로 |

**OAuth 심사 영향:** refresh token을 서버에 장기 보관하면 개인정보처리방침의 「Google 사용자 데이터」 · 「보존 기간」 항목을 고쳐야 하고, 심사 설명에 "사용자가 요청한 주간 요약을 보내기 위해 저장"을 적어야 한다. 보안 평가(CASA)는 restricted scope에 붙는 절차라 `analytics.readonly`에는 해당하지 않을 것으로 보이지만(분류는 Cloud Console 동의 화면의 scope 표시로 확인), 심사 신청 **전에** 이 기능을 넣을지 정하는 게 좋다(§8-1).

## 5. 발송 수단 비교

| | Resend | SendGrid | Amazon SES | Gmail API(사용자 본인) |
|---|---|---|---|---|
| 무료 범위 | 월 3,000통 · **하루 100통 상한** (2026-11 확인) | 확인 필요 | 사용량 과금 | — |
| 설정 | 도메인 DNS(SPF·DKIM) | 도메인 DNS | 도메인 DNS + 샌드박스 해제 신청 | 사용자마다 `gmail.send` 권한 |
| 장점 | API 단순, 개발 빠름 | 실적·기능 많음 | 가장 쌈, AWS 필요 | 발신자가 본인 |
| 단점 | 비교적 신생 | 무료 축소 경향 | AWS 계정·심사 | **restricted scope → 심사 부담 큼**, 비권장 |

권장: **Resend**(또는 SendGrid). 무료 플랜의 하루 100통 상한 때문에, 월요일 아침에 구독자가 100명을 넘으면 유료(Pro, 월 50,000통)로 올려야 한다. 발신 `report@sitekpi.net`, SPF · DKIM · DMARC 설정. 코드에는 `send_mail(to, subject, html, text, headers)` 한 함수만 두고 구현을 바꿔 끼울 수 있게 한다. 키가 없으면 로그만 남긴다(개발·테스트).

**준비된 것 (2026-11-23)**
- Resend 도메인 `sitekpi.net` 인증 완료 (Tokyo `ap-northeast-1`, DKIM `resend._domainkey` · SPF CNAME `rsend` · `send` · DMARC `_dmarc` `p=none`, DNS는 お名前.com). 받기(receiving)는 끔.
- API 키: Secret Manager `resend_mail` (프로젝트 `starful-258005`). 구현할 때 `cloudbuild.yaml`의 `--set-secrets`에 `RESEND_API_KEY=resend_mail:latest`를 더하고, Cloud Run 서비스 계정에 이 비밀값의 `roles/secretmanager.secretAccessor`를 준다(`scripts/gcp_setup.sh`). 다른 비밀값은 `SITEKPI_*` 이름이라, 이름을 맞추고 싶으면 그때 `SITEKPI_RESEND_API_KEY`로 새로 만들어도 된다.

> 가격·무료 범위는 2026-11 시점 각 서비스 페이지 기준으로 다시 확인할 것.

## 6. 법·약관 (일본 기준)

- **特定電子メール法**: 광고성 메일은 사전 동의(옵트인) · 발신자 이름/주소 · 수신 거부 방법 표시가 필요. 주간 요약은 서비스 알림 성격이지만, 안에 유료 플랜 안내 등을 넣으면 광고로 볼 수 있으므로 **처음부터 같은 요건을 지킨다**(더블 옵트인 · 하단에 운영자 표기 `OPERATOR_NAME` · `OPERATOR_ADDRESS` · 원클릭 정지).
- 개인정보처리방침: 「取得する情報」에 메일 주소, 「利用目的」에 알림 발송, 「委託と海外移転」에 메일 발송 업체(미국 등), 「保存期間」에 구독 해지 후 삭제 기한.
- 이용약관: 알림 내용의 성격(진단이 아님 — 보드와 같은 문구).
- 정해지지 않은 운영자명·주소(기획서 「정할 것」)가 **먼저 정해져야** 메일을 보낼 수 있다.

## 7. 측정

| 이벤트 (track.js / 서버) | 용도 |
|---|---|
| `mail_subscribe_open` · `mail_subscribe` · `mail_confirm` | 구독 퍼널 |
| `mail_sent` (서버, 종류 A/B/C) · `mail_click` (UTM `utm_source=mail&utm_campaign=weekly|change|effect`) | 열람 대신 클릭으로 판단(열람 추적 픽셀은 쓰지 않음) |
| `mail_unsubscribe` (이유 선택: 多い · 役に立たない · その他) | 피로도 |

성공 기준(첫 4주): 구독자의 28일 재방문율이 비구독 연결 사용자보다 높을 것. 주간 메일 클릭률 10% 이상.

## 8. 정할 것

1. **refresh token을 서버에 보관해도 되는가** (처리방침·심사 설명 변경). 안 된다면 → "보드를 열 때 지난주 요약을 보여 주기"만 가능(메일 없음).
2. 발송 업체 (권장 Resend).
3. 운영자명·주소 확정 (메일 하단 표기에 필요).
4. 무료/Pro: 주간 메일은 무료(재방문 목적), 여러 사이트 묶음 메일은 Pro(`site_compare`와 같이)로 할지.

## 9. 구현 순서 (정해진 뒤)

1. `send_mail` + Resend 구현 · 키 없으면 로그. 테스트는 가짜 발송기.
2. 구독 저장소(Firestore/SQLite 두 구현, 기존 store 패턴) · 토큰 암호화 · 더블 옵트인 · 원클릭 정지.
3. 메일 본문: `build_story` 결과 → Jinja 메일 템플릿(HTML + 텍스트, ja/en/ko). 보드 화면과 같은 문장인지 테스트.
4. `/cron/notify` + Cloud Scheduler(`scripts/gcp_setup.sh`에 추가) · OIDC 검증.
5. A 주간 메일 → B 판정 변화 → C 효과 결과 순서로 켠다(각각 2주씩 지표 확인).
6. 처리방침·약관·기획서·SPEC·릴리스 노트 갱신.
